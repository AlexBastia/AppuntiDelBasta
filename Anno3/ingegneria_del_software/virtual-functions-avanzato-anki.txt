[C++][Teoria] Cos'e' una <b>funzione virtuale</b>, e come si chiama la sua ridefinizione?	Un metodo <b>non statico</b> di una classe base che puo' essere &quot;ridefinito&quot; nelle classi derivate. La ridefinizione si chiama <b>overriding</b>.<br><br><i>(slide 5)</i>
[Teoria] Quali sono le <b>due condizioni</b> perche' avvenga overriding?	1. Il metodo sovrascritto (nella base) deve essere <b>virtual</b>.<br>2. Il metodo che sovrascrive (nella derivata) deve avere la <b>stessa signature</b> e lo <b>stesso return type</b>.<br><br>In certi linguaggi l'overriding puo' essere impedito (es. <code>final</code> in Java).<br><i>(slide 6)</i>
[Teoria] Cosa include la <b>signature</b> di una funzione? E il <b>prototype</b>?	<b>Signature</b> = nome + numero dei parametri formali + tipi dei parametri formali.<br>Il <b>return type NON e' incluso</b> nella signature.<br><br><b>Prototype</b> = signature + return type.<br><i>(slide 7)</i>
[Teoria] Quali sono le <b>tre possibilita'</b> quando una f() virtuale e' invocata su un oggetto <code>o</code> di classe D derivata da B?	1. <code>f</code> definita <b>solo in D</b> &rarr; si chiama D.f<br>2. <code>f</code> definita <b>solo in B</b> &rarr; si chiama B.f (ereditata)<br>3. <code>f</code> <b>overridden in D</b> &rarr; si chiama D.f (la versione overridden)<br><br>In tutti i casi si usa la <b>classe reale dell'oggetto</b>, NON la classe del riferimento/puntatore.<br><i>(slide 11)</i>
[Teoria] Quando emerge davvero il <b>vantaggio</b> delle funzioni virtuali?	Quando si manipolano oggetti tramite <b>riferimenti o puntatori alla classe base</b>: solo in quel caso il comportamento &quot;virtuale&quot; diventa visibile.<br><br>Chiamando il metodo su un oggetto il cui tipo e' gia' noto a compile-time, si comporta come un metodo non virtuale.<br><i>(slide 10, 12)</i>
[Teoria] Cos'e' l'<b>early binding</b> (compile-time binding)?	Il compilatore, incontrando una chiamata a funzione, scrive codice macchina che chiama un <b>indirizzo ben definito</b> (dove inizia il codice della funzione): &quot;lega&quot; il punto di chiamata al codice gia' a <b>compile time</b>.<br><br>E' il comportamento standard per funzioni e metodi C++ <b>non virtual</b>, e l'unico esistente nei linguaggi imperativi non-OO (C, Pascal).<br><i>(slide 29-30)</i>
[Teoria] Cos'e' il <b>late binding</b> (run-time binding)?	In presenza di funzioni virtuali il binding non puo' essere fatto a compile time: il compilatore <b>sa quale funzione e' virtual</b>, ma non puo' dedurre quale codice eseguire guardando solo la chiamata.<br><br>Scrive quindi codice macchina che <b>deduce l'indirizzo corretto a runtime</b>.<br><i>(slide 31)</i>
[Teoria] Cosa sono <b>VFT</b> e <b>VFTP</b>?	<b>VFT</b> (Virtual Function Table): tabella associata a <b>ogni classe</b> con funzioni virtuali, contiene i puntatori al codice di ciascuna funzione virtuale.<br><br><b>VFTP</b> (Virtual Function Table Pointer): puntatore <b>nascosto all'utente</b> che <b>ogni oggetto</b> di tale classe porta con se', e che punta alla VFT della propria classe.<br><br>Nota: &quot;pointer&quot; qui = puntatore C++ <i>oppure</i> riferimento Java.<br><i>(slide 33)</i>
[Teoria] Elenca i <b>5 passi</b> eseguiti a runtime per completare una chiamata late-bound.	1. dal puntatore/riferimento si raggiunge l'<b>oggetto</b><br>2. si cerca il <b>VFTP</b> nell'oggetto<br>3. tramite il VFTP si trova la <b>VFT della classe reale</b><br>4. si cerca nella VFT l'<b>entry giusta</b> (es. VFP2 per la funzione VF2)<br>5. tramite quel puntatore si raggiunge ed <b>esegue il codice corretto</b><br><i>(slide 35)</i>
[Teoria] Se il late binding e' cosi' comodo, perche' il C++ non rende tutto virtual (come fa Java)?	Per <b>efficienza</b>: il late binding e' relativamente costoso in tempo di esecuzione. Se un metodo e' chiamato molto di frequente ed e' semplice, l'overhead puo' diventare un collo di bottiglia.<br><br>In pratica pero' pochissimi punti di un programma medio sono cosi' critici: conta in <b>sistemi real-time</b>, <b>routine matematiche core</b>, <b>programmazione di sistema di basso livello</b>.<br><i>(slide 36-38)</i>
[C++][Cosa fa?] <br><div style="text-align:left; display:inline-block; margin:6px 0;"><code>struct B {<br>&nbsp;&nbsp;&nbsp;&nbsp;virtual void f() { cout &lt;&lt; "B::f\n"; }<br>&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;void g() { cout &lt;&lt; "B::g\n"; }<br>};<br>struct D : B {<br>&nbsp;&nbsp;&nbsp;&nbsp;void f() override { cout &lt;&lt; "D::f\n"; }<br>&nbsp;&nbsp;&nbsp;&nbsp;void g()          { cout &lt;&lt; "D::g\n"; }<br>};<br><br>int main() {<br>&nbsp;&nbsp;&nbsp;&nbsp;D d;<br>&nbsp;&nbsp;&nbsp;&nbsp;B* p = &amp;d;<br>&nbsp;&nbsp;&nbsp;&nbsp;p-&gt;f();<br>&nbsp;&nbsp;&nbsp;&nbsp;p-&gt;g();<br>&nbsp;&nbsp;&nbsp;&nbsp;d.f();<br>&nbsp;&nbsp;&nbsp;&nbsp;d.g();<br>}</code></div><br>Cosa stampa, riga per riga?	Output (verificato):<br><div style="text-align:left; display:inline-block; margin:6px 0;"><code>D::f<br>B::g<br>D::f<br>D::g</code></div><br><b>Perche':</b> <code>f()</code> e' virtual &rarr; late binding, si guarda la classe <b>reale</b> (D) anche tramite <code>B*</code>.<br><code>g()</code> NON e' virtual &rarr; early binding, si guarda il <b>tipo del puntatore</b> (B). Con <code>d.g()</code> il tipo statico e' gia' D, quindi sembra un override ma non lo e': e' <b>hiding</b>.<br><br><i>La prova che g() e' hiding: p-&gt;g() e d.g() stampano cose DIVERSE.</i><br><i>(prove/02)</i>
[C++][Cosa fa?] <br><div style="text-align:left; display:inline-block; margin:6px 0;"><code>struct B {<br>&nbsp;&nbsp;&nbsp;&nbsp;virtual void f(int i)    { cout &lt;&lt; "B::f(int) " &lt;&lt; i &lt;&lt; "\n"; }<br>&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;void f(double d){ cout &lt;&lt; "B::f(double) " &lt;&lt; d &lt;&lt; "\n"; }<br>};<br>struct D : B {<br>&nbsp;&nbsp;&nbsp;&nbsp;void f(int i) override { cout &lt;&lt; "D::f(int) " &lt;&lt; i &lt;&lt; "\n"; }<br>};<br><br>int main() {<br>&nbsp;&nbsp;&nbsp;&nbsp;D d;<br>&nbsp;&nbsp;&nbsp;&nbsp;d.f(3.14);<br>}</code></div><br>Cosa stampa? (attenzione, non e' quello che sembra)	Stampa:<br><div style="text-align:left; display:inline-block; margin:6px 0;"><code>D::f(int) 3</code></div><br><b>Perche':</b> <code>D::f(int)</code> <b>nasconde TUTTI</b> gli overload di <code>f</code> ereditati (<b>name hiding</b>). Il name lookup si ferma al primo scope che contiene il nome <code>f</code> (cioe' D), <b>prima</b> ancora di guardare quanti overload ci sono in B.<br>L'unico candidato e' <code>D::f(int)</code>, quindi 3.14 viene troncato a 3.<br><br><b>Tre fix:</b><br>1. <code>using B::f;</code> dentro D<br>2. chiamata qualificata <code>d.B::f(3.14)</code><br>3. ridichiarare l'overload in D<br>(il flag <code>-Woverloaded-virtual</code> lo intercetta)<br><i>(prove/03)</i>
[C++][Cosa fa?] <br><div style="text-align:left; display:inline-block; margin:6px 0;"><code>struct A {<br>&nbsp;&nbsp;&nbsp;&nbsp;A()          { cout &lt;&lt; "A() "; f(); }<br>&nbsp;&nbsp;&nbsp;&nbsp;virtual ~A() { cout &lt;&lt; "~A() "; g(); }<br>&nbsp;&nbsp;&nbsp;&nbsp;virtual void f() { cout &lt;&lt; "A::f\n"; }<br>&nbsp;&nbsp;&nbsp;&nbsp;virtual void g() { cout &lt;&lt; "A::g\n"; }<br>};<br>struct B : A {<br>&nbsp;&nbsp;&nbsp;&nbsp;int x = 42;<br>&nbsp;&nbsp;&nbsp;&nbsp;void f() override { cout &lt;&lt; "B::f (x=" &lt;&lt; x &lt;&lt; ")\n"; }<br>&nbsp;&nbsp;&nbsp;&nbsp;void g() override { cout &lt;&lt; "B::g (x=" &lt;&lt; x &lt;&lt; ")\n"; }<br>};<br><br>int main() { B b; }</code></div><br>Cosa stampa? Perche' NON si vede mai B::f ne' B::g?	Output (verificato):<br><div style="text-align:left; display:inline-block; margin:6px 0;"><code>A() A::f<br>~A() A::g</code></div><br><b>Perche':</b> il tipo dinamico di un oggetto C++ <b>cresce</b> durante la costruzione e <b>decresce</b> durante la distruzione.<br><br>&bull; Nel corpo del ctor di A, l'oggetto E' ancora un A (il vptr punta alla vtable di A) &rarr; <code>A::f</code>.<br>&bull; <code>~A()</code> gira <b>dopo</b> <code>~B()</code>: il vptr e' gia' tornato ad A &rarr; <code>A::g</code>.<br><br><b>E' una protezione:</b> se si chiamasse B::f dal ctor di A, leggerebbe <code>x</code> non ancora inizializzato.<br><i>(prove/04)</i>
[C++][Cosa fa?] <br><div style="text-align:left; display:inline-block; margin:6px 0;"><code>struct A { virtual void f() { cout &lt;&lt; "A::f\n"; } };<br>struct B : virtual A { void f() override { cout &lt;&lt; "B::f\n"; } };<br>struct C : virtual A { };<br>struct D : B, C { };<br><br>int main() {<br>&nbsp;&nbsp;&nbsp;&nbsp;D d;<br>&nbsp;&nbsp;&nbsp;&nbsp;d.f();<br>}</code></div><br>Compila? Cosa stampa? Come si chiama la regola in gioco?	Compila e stampa:<br><div style="text-align:left; display:inline-block; margin:6px 0;"><code>B::f</code></div><br><b>Regola: DOMINANZA.</b><br>Con le basi <b>virtual</b> esiste un <b>solo</b> sotto-oggetto A condiviso; <code>B::f</code> e' un override di quell'unico <code>A::f</code>, quindi <b>domina</b> su di esso.<br>Il <i>final overrider</i> e' unico &rarr; nessuna ambiguita'.<br><br><b>Verifica dell'unicita':</b> castando <code>&amp;d</code> ad A* via B e via C si ottiene lo <b>stesso indirizzo</b>.<br><i>(prove/06)</i>
[C++][Cosa fa?] <br><div style="text-align:left; display:inline-block; margin:6px 0;"><code>struct A { virtual void f() { cout &lt;&lt; "A::f\n"; } };<br>struct B : A { void f() override { cout &lt;&lt; "B::f\n"; } };<br>struct C : A { };<br>struct D : B, C { };<br><br>int main() {<br>&nbsp;&nbsp;&nbsp;&nbsp;D d;<br>&nbsp;&nbsp;&nbsp;&nbsp;d.f();<br>}</code></div><br>Uguale al precedente ma <b>senza</b> <code>virtual</code> nelle basi. Cosa cambia?	<b>NON compila.</b> Errore reale di GCC:<br><div style="text-align:left; display:inline-block; margin:6px 0;"><code>error: request for member 'f' is ambiguous<br>note: candidates are: 'virtual void A::f()'<br>note:                 'virtual void B::f()'</code></div><br><b>Perche':</b> senza <code>virtual</code> ci sono <b>DUE</b> sotto-oggetti A distinti in D (uno via B, uno via C), quindi due <code>f()</code> candidate: quella overridden in B, e quella originale di A raggiunta via C. Nessuna delle due domina l'altra.<br><br><b>Fix:</b> chiamata qualificata <code>d.B::f();</code> (si sceglie <b>attraverso quale sotto-oggetto A</b> passare).<br><i>(prove/07)</i>
[C++][Cosa fa?] <br><div style="text-align:left; display:inline-block; margin:6px 0;"><code>struct A { A(const char* who) { cout &lt;&lt; "A(" &lt;&lt; who &lt;&lt; ") "; } };<br>struct B : virtual A { B() : A("da B") { cout &lt;&lt; "B() "; } };<br>struct C : virtual A { C() : A("da C") { cout &lt;&lt; "C() "; } };<br>struct D : B, C  { D() : A("da D"), B(), C() { cout &lt;&lt; "D() "; } };<br>struct E : D     { E() : A("da E"), D()      { cout &lt;&lt; "E() "; } };<br><br>int main() { E e; }</code></div><br>Quale fra &quot;da B/C/D/E&quot; viene stampato? Uno solo o tutti?	Output (verificato):<br><div style="text-align:left; display:inline-block; margin:6px 0;"><code>A(da E) B() C() D() E()</code></div><br><b>Un solo A(...), quello di E.</b><br><br><b>Regola:</b> la base virtuale e' inizializzata <b>sempre dalla classe MOST DERIVED</b> (qui E). I mem-initializer per A scritti in B, C e D vengono <b>ignorati</b> in questa costruzione.<br><br>Costruendo un <code>D d;</code> da solo, invece, vincerebbe &quot;da D&quot;. Lo stesso mem-initializer viene usato o ignorato a seconda del ruolo della classe in quella costruzione.<br><i>(prove/08)</i>
[C++][Cosa fa?] <br><div style="text-align:left; display:inline-block; margin:6px 0;"><code>struct I {<br>&nbsp;&nbsp;&nbsp;&nbsp;virtual void f() = 0;<br>&nbsp;&nbsp;&nbsp;&nbsp;virtual ~I() = default;<br>};<br>struct L : virtual I { void f() override { cout &lt;&lt; "L::f\n"; } };<br>struct R : virtual I { };<br>struct D : L, R { };<br><br>int main() {<br>&nbsp;&nbsp;&nbsp;&nbsp;D d;<br>&nbsp;&nbsp;&nbsp;&nbsp;d.f();<br>}</code></div><br>D e' istanziabile, dato che R non implementa f()?	<b>Si', compila e stampa</b> <code>L::f</code>.<br><br>Con ereditarieta' <b>virtuale</b> esiste un <b>solo</b> sotto-oggetto I: per dominanza il final overrider unico e' <code>L::f</code>. Il ramo R &quot;eredita gratis&quot; l'implementazione dall'altra parte del diamante.<br><br><b>Regola:</b> in un diamante virtuale un metodo puro va implementato <b>una volta sola</b>.<br><br><b>Togliendo <code>virtual</code></b> dalle basi: due I distinti, quello via R ha ancora f() pura &rarr; D resta <b>astratta</b>, non istanziabile.<br><i>(prove/09)</i>
[C++][Verificato] <br><div style="text-align:left; display:inline-block; margin:6px 0;"><code>struct Base {<br>&nbsp;&nbsp;&nbsp;&nbsp;virtual void f() = 0;<br>&nbsp;&nbsp;&nbsp;&nbsp;Base() { f(); }<br>};<br>struct Derivata : Base {<br>&nbsp;&nbsp;&nbsp;&nbsp;void f() override { cout &lt;&lt; "Derivata::f\n"; }<br>};<br><br>int main() { Derivata d; }</code></div><br>Chiamata a una virtuale <b>pura</b> dal costruttore: crash a runtime? Cosa succede DAVVERO?	<b>NON e' un crash a runtime: e' un ERRORE DI LINK</b> (verificato, g++ 15.2.1):<br><div style="text-align:left; display:inline-block; margin:6px 0;"><code>undefined reference to `Base::f()'</code></div><br><b>Perche':</b> dentro il ctor di Base il compilatore <b>sa</b> che il tipo dinamico e' esattamente Base (non ancora Derivata), quindi <b>devirtualizza</b> la chiamata in una chiamata diretta a <code>Base::f()</code>. Ma quel simbolo non esiste (pura, senza corpo) &rarr; se ne accorge il <b>linker</b>.<br><br><i>La teoria dice &quot;UB&quot;; nella pratica di questa toolchain l'errore arriva prima, a link time.</i><br><i>(prove/05)</i>
[C++][Trabocchetto] Una funzione virtuale <b>pura</b> (<code>= 0</code>) puo' avere un <b>corpo</b>? Se si', come lo si chiama?	<b>SI'</b> — e' un &quot;corner case&quot; citato dai riferimenti di Wikipedia (Raymond Chen, <i>&quot;C++ corner case: you can implement pure virtual functions in the base class&quot;</i>).<br><br><br><div style="text-align:left; display:inline-block; margin:6px 0;"><code>struct Base {<br>&nbsp;&nbsp;&nbsp;&nbsp;virtual void f() = 0;      // dichiarata pura...<br>&nbsp;&nbsp;&nbsp;&nbsp;Base() { f(); }<br>};<br>void Base::f() {               // ...ma con un corpo!<br>&nbsp;&nbsp;&nbsp;&nbsp;cout &lt;&lt; "Base::f (default)\n";<br>}<br>struct Derivata : Base {<br>&nbsp;&nbsp;&nbsp;&nbsp;void f() override { cout &lt;&lt; "Derivata::f\n"; }<br>};</code></div><br><code>= 0</code> impone solo che le derivate <b>concrete</b> facciano l'override: <b>non vieta</b> un'implementazione di default.<br>Il corpo e' invocabile solo per <b>chiamata qualificata</b> (<code>Base::f()</code>) o, come qui, dal ctor della classe stessa: non finisce mai in vtable come &quot;la&quot; implementazione.<br><b>Con il corpo, il programma sopra compila e stampa &quot;Base::f (default)&quot;.</b><br><i>(prove/05, variante B)</i>
[C++][Verificato][Trabocchetto] La slide 18 dice: &quot;In C++ non esiste una keyword come <code>final</code> di Java, non e' possibile impedire l'hiding&quot;. E' ancora vero?	<b>La slide e' datata.</b> Da <b>C++11</b> la keyword <code>final</code> esiste e funziona (verificato con g++):<br><div style="text-align:left; display:inline-block; margin:6px 0;"><code>struct B { virtual void f() { } };<br>struct D : B { void f() final { } };   // nessuno potra' piu' overridare f<br>struct E : D { void f() { } };         // ERRORE di compilazione</code></div>Errore reale prodotto:<br><div style="text-align:left; display:inline-block; margin:6px 0;"><code>error: virtual function 'virtual void E::f()'&lt;br&gt;overriding final function</code></div><br>Si puo' marcare <code>final</code> anche un'<b>intera classe</b> (<code>struct D final : B { };</code>) per impedirne la derivazione, come in Java.<br><br><b>Resta vero</b> il punto sostanziale della slide: <code>final</code> impedisce l'<b>override</b>, ma non impedisce l'<b>hiding</b> di un nome non virtuale in una derivata.

[C++][Scrivi] <b>Scrivi</b> il pattern <b>NVI</b> (Non-Virtual Interface): una classe <code>Task</code> con interfaccia pubblica <b>non virtuale</b> <code>run()</code> che stampa un prologo, chiama il punto di variazione, e stampa un epilogo. Il punto di variazione deve essere <b>virtuale privato</b>. Poi due derivate concrete.	<br><div style="text-align:left; display:inline-block; margin:6px 0;"><code>#include &lt;iostream&gt;<br>#include &lt;vector&gt;<br>#include &lt;string&gt;<br><br>class Task {<br>public:<br>&nbsp;&nbsp;&nbsp;&nbsp;void run() {                      // pubblico, NON virtuale<br>&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;std::cout &lt;&lt;       // virtuale PRIVATO<br>};<br><br>class PrintTask : public Task {<br>&nbsp;&nbsp;&nbsp;&nbsp;std::string msg;<br>public:<br>&nbsp;&nbsp;&nbsp;&nbsp;PrintTask(std::string m) : msg(std::move(m)) {}<br>private:<br>&nbsp;&nbsp;&nbsp;&nbsp;void execute() override {         // override di un metodo privato: OK!<br>&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;std::cout &lt;&lt; "PrintTask: " &lt;&lt; msg &lt;&lt; "\n";<br>&nbsp;&nbsp;&nbsp;&nbsp;}<br>};<br><br>class SumTask : public Task {<br>&nbsp;&nbsp;&nbsp;&nbsp;int a, b;<br>public:<br>&nbsp;&nbsp;&nbsp;&nbsp;SumTask(int a_, int b_) : a(a_), b(b_) {}<br>private:<br>&nbsp;&nbsp;&nbsp;&nbsp;void execute() override {<br>&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;std::cout &lt;&lt; [C++][Teoria] Cos'e' il <b>diamond problem</b> e cosa garantisce l'<b>ereditarieta' virtuale</b>?	<b>Diamond problem:</b> se B e C derivano da A, e D deriva da B e C, allora un oggetto D contiene <b>due copie</b> delle variabili membro di A (una via B, una via C), accessibili indipendentemente con lo scope resolution.<br><br><b>Ereditarieta' virtuale:</b> tecnica che garantisce che venga ereditata <b>una sola copia</b> della base:<br><div style="text-align:left; display:inline-block; margin:6px 0;"><code>class Derived : virtual public Base { };</code></div><i>(Wikipedia, &quot;Virtual inheritance&quot;)</i>
[C++][Teoria] <b>Chi</b> inizializza una base virtuale, e cosa succede ai mem-initializer scritti nelle classi intermedie?	La base virtuale e' inizializzata <b>sempre dal costruttore della classe MOST DERIVED</b> (quella dell'oggetto che si sta effettivamente creando).<br><br>Tutti i mem-initializer per quella base scritti nelle classi <b>intermedie</b> vengono <b>IGNORATI</b> quando quelle classi non sono l'oggetto most-derived.<br><br><b>Perche':</b> impedisce che piu' classi intermedie inizializzino la base condivisa piu' volte.<br><br><b>Conseguenza pratica:</b> se la base virtuale non ha un ctor di default, <b>ogni</b> classe concreta della gerarchia (a qualunque profondita') e' obbligata a nominarla esplicitamente.<br><i>(Thinking in C++ vol.2 cap.9; prove/08)</i>
[C++][Teoria] Qual e' l'<b>ordine di costruzione</b> dei sotto-oggetti in una gerarchia con basi virtuali?	1. tutte le <b>basi virtuali</b> (in ordine depth-first, sinistra&rarr;destra, sulla gerarchia della classe most-derived)<br>2. le <b>basi non virtuali</b>, in ordine di dichiarazione<br>3. i <b>membri</b>, in ordine di dichiarazione<br>4. il <b>corpo</b> del costruttore<br><br>La <b>distruzione</b> avviene in ordine esattamente inverso.
[C++][Teoria] Nell'esempio Animal/Mammal/WingedAnimal/Bat, il layout di Bat con ereditarieta' virtuale e':<br><div style="text-align:left; display:inline-block; margin:6px 0;"><code>(vpointer, Mammal, vpointer, WingedAnimal, Bat, Animal)</code></div>Perche' Animal e' <b>in fondo</b>? Perche' <b>due</b> vpointer?	<b>Animal in fondo:</b> Mammal e WingedAnimal devono conservare il layout che avrebbero <b>da soli</b> (cosi' il codice compilato per Mammal continua a funzionare). L'unica copia condivisa va quindi in una posizione che non appartiene a nessuno dei due rami.<br><br><b>Due vpointer:</b> ogni ramo deve sapere &quot;quanto dista da qui il mio Animal&quot; (<b>vbase offset</b>), e quella distanza <b>non e' nota a compile time</b>: dipende da come il sotto-oggetto e' immerso nell'oggetto completo (un Mammal autonomo vs. un Mammal dentro un Bat).<br><br><b>Costo:</b> l'oggetto cresce di due puntatori rispetto alla versione non virtuale.<br><i>(Wikipedia, &quot;Virtual inheritance&quot;)</i>
[C++][Trabocchetto] Perche' <code>static_cast</code> da un puntatore a <b>base virtuale</b> verso la derivata e' <b>vietato</b>? Cosa si usa?	Perche' il compilatore dovrebbe sottrarre un <b>offset che non conosce staticamente</b> (il vbase offset e' noto solo a runtime, dalla vtable).<br><div style="text-align:left; display:inline-block; margin:6px 0;"><code>Animal* pa = &amp;bat;<br>Bat* p1 = static_cast&lt;Bat*&gt;(pa);    // ILL-FORMED<br>Bat* p2 = dynamic_cast&lt;Bat*&gt;(pa);   // OK</code></div>E' l'<b>unico caso</b> in cui <code>dynamic_cast</code> e' <b>obbligatorio</b> pur non essendoci alcuna incertezza sul tipo effettivo dell'oggetto.
[C++][Teoria] Qual e' il <b>criterio</b> per decidere se una base va ereditata virtualmente? Un esempio reale nella libreria standard?	<b>Criterio:</b> usa <code>virtual</code> quando l'ereditarieta' esprime una <b>restrizione di un insieme</b> (un Bat <i>e'</i> un Animal, uno solo). Non serve quando esprime <b>composizione di parti</b> indipendenti, dove copie separate sono coerenti.<br><br><b>Esempio reale:</b> <code>basic_istream</code> e <code>basic_ostream</code> derivano <b>virtualmente</b> da <code>basic_ios</code>, cosi' che <code>basic_iostream</code> (da cui <code>stringstream</code>, <code>fstream</code>) abbia <b>un solo</b> stato di stream condiviso invece di due (un solo buffer, un solo set di flag di errore).
[Java][Teoria] In Java, quali metodi sono virtual? Come si impedisce l'override?	In Java <b>tutti i metodi non statici sono virtual</b>: l'overriding e' sempre un'opzione, e avviene <b>automaticamente</b> (nessuna keyword <code>virtual</code> da scrivere).<br><br><b>Per impedirlo:</b> <code>final</code> sul metodo.<br><b>Per impedire l'estensione:</b> <code>final</code> sull'intera classe.<br><br><b>Non possono essere overridden:</b> <code>final</code>, <code>private</code>, <code>static</code>.<br><i>(slide 16)</i>

[Trasv][Trabocchetto] Distingui con precisione: <b>overriding</b>, <b>overloading</b>, <b>hiding/shadowing</b>, <b>dominanza</b>.	&bull; <b>Overriding</b>: stessa firma, risolto sul tipo <b>dinamico</b>. C++ (solo se <code>virtual</code>), Java (default), Python (sempre).<br><br>&bull; <b>Overloading</b>: stesso nome, parametri diversi, risolto a <b>compile time</b>. C++ e Java. [C++][Teoria] A cosa serve la keyword <code>override</code> del C++11, se l'override funziona anche senza?	E' un <b>controllo per il compilatore</b>, esattamente come <code>@Override</code> in Java: dice &quot;questo metodo DEVE sovrascrivere un virtuale della base&quot;.<br><div style="text-align:left; display:inline-block; margin:6px 0;"><code>struct B { virtual void f(int) const; };<br><br>struct D : B {<br>&nbsp;&nbsp;&nbsp;&nbsp;void f(int);              // compila! ma NON e' un override (manca const)<br>&nbsp;&nbsp;&nbsp;&nbsp;void f(int) override;     // ERRORE esplicito: nessun match<br>};</code></div><b>Senza <code>override</code></b>, una firma leggermente sbagliata (un <code>const</code> mancante, un tipo di parametro diverso) produce silenziosamente un <b>nuovo metodo che nasconde</b> quello della base: il codice compila e si comporta male a runtime.<br><br><b>Regola:</b> metti sempre <code>override</code> sugli override, e <code>final</code> dove vuoi chiudere la gerarchia.
[C++][Teoria] Cosa cambia, per il <b>compilatore</b>, tra <code>override</code> e <code>final</code>?	&bull; <code>override</code> e' <b>solo un controllo</b>: verifica che l'override esista davvero. Non cambia il codice generato.<br><br>&bull; <code>final</code> e' un'<b>informazione semantica</b>: garantisce che nessuno potra' piu' fare l'override. Questo permette al compilatore di <b>devirtualizzare</b> la chiamata (risolverla staticamente) e quindi di <b>inlinearla</b>, anche senza LTO o analisi dell'intero programma.<br><br><b>Analogia Java:</b> la JVM ottiene lo stesso effetto a runtime con la <b>Class Hierarchy Analysis</b> (se una sola classe caricata implementa il metodo, devirtualizza speculativamente, con un guard e deottimizzazione se poi ne viene caricata un'altra).
[Trasv][Teoria] Qual e' il costo del polimorfismo dinamico nei quattro linguaggi?	&bull; <b>C++</b>: 2 load (vptr, poi lo slot) + una chiamata indiretta. Un puntatore per <b>oggetto</b>, una tabella per <b>classe</b>. Devirtualizzabile con <code>final</code>/LTO. E' lo <i>zero-overhead principle</i>: paghi solo se usi <code>virtual</code>.<br><br>&bull; <b>Java</b>: uguale in linea di principio, ma il JIT spesso <b>inlina per speculazione</b> (CHA + inline cache mono/bimorfiche), recuperando gran parte del costo.<br><br>&bull; <b>Python</b>: il piu' alto &mdash; lookup nel dizionario lungo l'MRO + creazione del bound method (mitigato da cache interne).<br><br>&bull; <b>C</b>: identico al C++, perche' e' letteralmente la stessa cosa scritta a mano.

[Trasv][Trabocchetto] &quot;Un metodo <code>static</code> puo' essere overridden?&quot; Rispondi per C++, Java e Python.	<b>No in nessuno dei tre</b>, ma per sfumature diverse:<br><br>&bull; <b>C++</b>: un metodo <code>static</code> non ha <code>this</code>, quindi non c'e' alcun ricevitore su cui fare dispatch: non puo' essere <code>virtual</code> (errore di compilazione se ci provi). Puo' solo essere <b>nascosto</b> da un omonimo nella derivata.<br><br>&bull; <b>Java</b>: idem &mdash; ridichiararlo nella derivata produce <b>hiding di metodo statico</b>, non override. La chiamata e' compilata in <code>invokestatic</code> sul <b>tipo statico</b>:<br><div style="text-align:left; display:inline-block; margin:6px 0;"><code>class A { static String s() { return "A"; } }<br>class B extends A { static String s() { return "B"; } }<br><br>A a = new B();<br>System.out.println(a.s());   // stampa "A", non "B"!</code></div>&bull; <b>Python</b>: uno <code>@staticmethod</code> si puo' ridefinire (tutto e' un attributo di classe), ma perde qualunque informazione sul chiamante. Per una factory polimorfica serve un <code>@classmethod</code>, dove <code>cls</code> e' il tipo reale su cui e' avvenuta la chiamata.

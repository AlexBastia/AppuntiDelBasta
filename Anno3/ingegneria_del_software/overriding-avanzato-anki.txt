[C++][A1] <div style="text-align:left; display:inline-block; margin-bottom:6px;"><code>struct A {<br>&nbsp;&nbsp;&nbsp;&nbsp;A() { std::cout &lt;&lt; "A() "; f(); }<br>&nbsp;&nbsp;&nbsp;&nbsp;virtual ~A() { g(); }<br>&nbsp;&nbsp;&nbsp;&nbsp;virtual void f() { std::cout &lt;&lt; "A::f "; }<br>&nbsp;&nbsp;&nbsp;&nbsp;virtual void g() { std::cout &lt;&lt; "A::g "; }<br>};<br>struct B : A {<br>&nbsp;&nbsp;&nbsp;&nbsp;int x = 42;<br>&nbsp;&nbsp;&nbsp;&nbsp;void f() override { std::cout &lt;&lt; "B::f " &lt;&lt; x &lt;&lt; " "; }<br>&nbsp;&nbsp;&nbsp;&nbsp;void g() override { std::cout &lt;&lt; "B::g "; }<br>};<br>int main() { B b; }</code></div><br>Classe <code>A</code> ha ctor che chiama <code>f()</code> virtual, e dtor <code>virtual</code> che chiama <code>g()</code> virtual; <code>B</code> deriva e fa l'override di entrambe. Cosa succede al dispatch di <code>f()</code> e <code>g()</code> durante costruzione e distruzione di un <code>B</code>?	Durante il ctor di <code>A</code> il tipo dinamico dell'oggetto <b>è ancora <code>A</code></b> (il vptr punta alla vtable di <code>A</code>): <code>f()</code> chiama <code>A::f</code>, non <code>B::f</code>. Simmetricamente, nel dtor di <code>A</code> (eseguito <b>dopo</b> <code>~B</code>) il vptr è già tornato ad <code>A</code>: <code>g()</code> chiama <code>A::g</code>. Il tipo dinamico "cresce" durante la costruzione e "decresce" durante la distruzione.

[C++][A1] <div style="text-align:left; display:inline-block; margin-bottom:6px;"><code>struct A {<br>&nbsp;&nbsp;&nbsp;&nbsp;A() { std::cout &lt;&lt; "A() "; f(); }<br>&nbsp;&nbsp;&nbsp;&nbsp;virtual ~A() { g(); }<br>&nbsp;&nbsp;&nbsp;&nbsp;virtual void f() { std::cout &lt;&lt; "A::f "; }<br>&nbsp;&nbsp;&nbsp;&nbsp;virtual void g() { std::cout &lt;&lt; "A::g "; }<br>};<br>struct B : A {<br>&nbsp;&nbsp;&nbsp;&nbsp;int x = 42;<br>&nbsp;&nbsp;&nbsp;&nbsp;void f() override { std::cout &lt;&lt; "B::f " &lt;&lt; x &lt;&lt; " "; }<br>&nbsp;&nbsp;&nbsp;&nbsp;void g() override { std::cout &lt;&lt; "B::g "; }<br>};<br>int main() { B b; }</code></div><br>Perché in C++ non bisogna mai chiamare funzioni virtuali dal costruttore o dal distruttore aspettandosi il dispatch dinamico sulla classe derivata?	Perché durante costruzione/distruzione il <b>vptr</b> punta sempre alla classe il cui ctor/dtor è in esecuzione in quel momento, <u>non</u> alla classe più derivata: la chiamata virtuale risolve alla versione della classe "corrente".

[C++][A1] <div style="text-align:left; display:inline-block; margin-bottom:6px;"><code>struct A {<br>&nbsp;&nbsp;&nbsp;&nbsp;A() { std::cout &lt;&lt; "A() "; f(); }<br>&nbsp;&nbsp;&nbsp;&nbsp;virtual ~A() { g(); }<br>&nbsp;&nbsp;&nbsp;&nbsp;virtual void f() { std::cout &lt;&lt; "A::f "; }<br>&nbsp;&nbsp;&nbsp;&nbsp;virtual void g() { std::cout &lt;&lt; "A::g "; }<br>};<br>struct B : A {<br>&nbsp;&nbsp;&nbsp;&nbsp;int x = 42;<br>&nbsp;&nbsp;&nbsp;&nbsp;void f() override { std::cout &lt;&lt; "B::f " &lt;&lt; x &lt;&lt; " "; }<br>&nbsp;&nbsp;&nbsp;&nbsp;void g() override { std::cout &lt;&lt; "B::g "; }<br>};<br>int main() { B b; }</code></div><br>Cosa succede se una funzione virtuale <b>pura</b> (<code>= 0</code>) viene chiamata, direttamente o indirettamente, dal costruttore della classe che la dichiara?	È <b>undefined behavior</b>. Non è un errore di compilazione perché il compilatore in generale non può dimostrare che la chiamata avverrà; in pratica molte implementazioni mettono in vtable <code>__cxa_pure_virtual</code>, che termina il programma con "pure virtual method called".

[C++][A2] <div style="text-align:left; display:inline-block; margin-bottom:6px;"><code>struct Base { virtual void f(int x = 10) { std::cout &lt;&lt; "Base " &lt;&lt; x; } };<br>struct Der : Base { void f(int x = 20) override { std::cout &lt;&lt; "Der " &lt;&lt; x; } };<br>int main() { Base* p = new Der; p-&gt;f(); }</code></div><br>In una funzione virtuale con <b>argomenti di default</b> diversi tra base e derivata, chiamata tramite puntatore alla base, quale corpo viene eseguito e quali default vengono usati?	Il <b>corpo</b> è scelto dinamicamente (tipo dinamico dell'oggetto); gli <b>argomenti di default</b> sono risolti staticamente in base al <b>tipo statico</b> del puntatore/riferimento. Risultato: si esegue il corpo della derivata coi default della base.

[C++][A2] <div style="text-align:left; display:inline-block; margin-bottom:6px;"><code>struct Base { virtual void f(int x = 10) { std::cout &lt;&lt; "Base " &lt;&lt; x; } };<br>struct Der : Base { void f(int x = 20) override { std::cout &lt;&lt; "Der " &lt;&lt; x; } };<br>int main() { Base* p = new Der; p-&gt;f(); }</code></div><br>Qual è la regola pratica per evitare il problema degli argomenti di default incoerenti tra base e override?	Non ridefinire mai i default in un override: se servono default diversi, usare il pattern <b>NVI</b> (funzione pubblica non virtuale col default, punto di variazione virtuale privato senza default).

[C++][A3] <div style="text-align:left; display:inline-block; margin-bottom:6px;"><code>struct B { virtual void f(int);  void f(double); };<br>struct D : B { void f(int) override; };<br>D d;  d.f(3.14);</code></div><br>Se una derivata <code>D</code> ridefinisce un solo overload <code>f(int)</code> di una base con più overload (<code>f(int)</code>, <code>f(double)</code>), perché <code>d.f(3.14)</code> non usa <code>f(double)</code> della base?	Perché <code>D::f(int)</code> <b>nasconde (name hiding)</b> tutti gli overload di <code>f</code> ereditati: il name lookup si ferma al primo scope (<code>D</code>) che contiene il nome, prima che parta l'overload resolution. <code>3.14</code> viene quindi convertito (troncato) a <code>int</code>.

[C++][A3] <div style="text-align:left; display:inline-block; margin-bottom:6px;"><code>struct B { virtual void f(int);  void f(double); };<br>struct D : B { void f(int) override; };<br>D d;  d.f(3.14);</code></div><br>Quali sono i tre modi per correggere il name hiding degli overload in una classe derivata?	(1) <code>using B::f;</code> dentro <code>D</code>; (2) chiamata qualificata <code>d.B::f(3.14)</code>; (3) ridichiarare esplicitamente anche l'overload mancante in <code>D</code>. Il flag <code>-Woverloaded-virtual</code> intercetta il caso.

[C++][A4] <div style="text-align:left; display:inline-block; margin-bottom:6px;"><code>struct A { virtual void f() { std::cout &lt;&lt; "A"; } };<br>struct B : virtual A { void f() override { std::cout &lt;&lt; "B"; } };<br>struct C : virtual A { };<br>struct D : B, C { };<br>int main() { D d; d.f(); }</code></div><br>In un diamante con ereditarietà <b>virtuale</b> (<code>B</code>, <code>C</code> virtual <code>A</code>; <code>D : B, C</code>), se solo <code>B</code> fa l'override di <code>f()</code>, quale versione chiama un oggetto <code>D</code>, e perché?	<code>B::f()</code>, per la regola di <b>dominanza</b>: con basi virtuali esiste un solo sotto-oggetto <code>A</code> condiviso, e <code>B::f</code> domina <code>A::f</code>. Il final overrider è unico: nessuna ambiguità.

[C++][A4] <div style="text-align:left; display:inline-block; margin-bottom:6px;"><code>struct A { virtual void f() { std::cout &lt;&lt; "A"; } };<br>struct B : virtual A { void f() override { std::cout &lt;&lt; "B"; } };<br>struct C : virtual A { };<br>struct D : B, C { };<br>int main() { D d; d.f(); }</code></div><br>Cosa cambia nel diamante se le basi <b>non</b> sono dichiarate <code>virtual</code>?	Esistono <b>due</b> sotto-oggetti <code>A</code> distinti: <code>d.f()</code> diventa <b>ambiguo</b> (errore di compilazione), serve <code>d.B::f()</code>.

[C++][A4] <div style="text-align:left; display:inline-block; margin-bottom:6px;"><code>struct A { virtual void f() { std::cout &lt;&lt; "A"; } };<br>struct B : virtual A { void f() override { std::cout &lt;&lt; "B"; } };<br>struct C : virtual A { };<br>struct D : B, C { };<br>int main() { D d; d.f(); }</code></div><br>Nel diamante virtuale, se anche <code>C</code> facesse l'override di <code>f()</code> (oltre a <code>B</code>), quando esattamente il programma diventa ill-formed?	Alla <b>definizione di <code>D</code></b>, non al punto di chiamata: non esiste più un final overrider unico. È ill-formed a meno che <code>D</code> non fornisca il proprio override, che domina entrambi.

[C++][A5] <div style="text-align:left; display:inline-block; margin-bottom:6px;"><code>struct A { virtual void f(); int a; };<br>struct B { virtual void g(); int b; };<br>struct C : A, B { void f() override; void g() override; };<br>C c;  B* pb = &amp;c;      // (void*)pb != (void*)&amp;c<br>pb-&gt;g();</code></div><br>In ereditarietà multipla (<code>C : A, B</code>), con <code>B* pb = &amp;c;</code> (indirizzo diverso da <code>&amp;c</code> castato a <code>void*</code>) e chiamata <code>pb->g()</code>, chi aggiusta <code>this</code> perché punti all'inizio di <code>C</code>?	Un <b>thunk</b>: nella vtable secondaria (del sotto-oggetto <code>B</code> dentro <code>C</code>) l'entry per <code>g</code> non punta direttamente a <code>C::g</code>, ma a un trampolino che fa <code>this -= offset</code> e poi salta a <code>C::g</code> (Itanium ABI: "non-virtual this adjustment").

[C++][A5] <div style="text-align:left; display:inline-block; margin-bottom:6px;"><code>struct A { virtual void f(); int a; };<br>struct B { virtual void g(); int b; };<br>struct C : A, B { void f() override; void g() override; };<br>C c;  B* pb = &amp;c;      // (void*)pb != (void*)&amp;c<br>pb-&gt;g();</code></div><br>In ereditarietà multipla non virtuale (<code>C : A, B</code>), quanti vptr contiene un oggetto <code>C</code>, e perché?	<b>Due</b>: uno per il sotto-oggetto primario (<code>A</code>) e uno per quello secondario (<code>B</code>), perché ciascun ramo ha bisogno del proprio dispatch e del proprio aggiustamento di offset.

[C++][A5] <div style="text-align:left; display:inline-block; margin-bottom:6px;"><code>struct A { virtual void f(); int a; };<br>struct B { virtual void g(); int b; };<br>struct C : A, B { void f() override; void g() override; };<br>C c;  B* pb = &amp;c;      // (void*)pb != (void*)&amp;c<br>pb-&gt;g();</code></div><br>Come si recupera l'indirizzo dell'oggetto <b>most derived</b> (<code>C</code>) partendo da un puntatore <code>B*</code> al sotto-oggetto <code>B</code>?	Con <code>dynamic_cast&lt;void*&gt;(pb)</code>, che usa l'<b>offset-to-top</b> memorizzato nella vtable.

[C++][A6] <div style="text-align:left; display:inline-block; margin-bottom:6px;"><code>virtual void f(int) const noexcept;   // base<br>void f(int) const;                    // candidato (b)</code></div><br>Data <code>virtual void f(int) const noexcept;</code> nella base, <code>void f(int) const</code> (senza <code>noexcept</code>) nella derivata è un override legale?	No: da C++17 <code>noexcept</code> fa parte del tipo della funzione, e un override non può essere <b>meno restrittivo</b> della base (il contrario è invece legale).

[C++][A6] <div style="text-align:left; display:inline-block; margin-bottom:6px;"><code>virtual void f(int) const noexcept;   // base<br>void f(long) const noexcept;          // candidato (d)</code></div><br>Data <code>virtual void f(int) const noexcept;</code> nella base, <code>void f(long) const noexcept</code> nella derivata è un override?	No: parametri diversi (<code>int</code> vs <code>long</code>) → è un overload che nasconde il virtuale, non un override.

[C++][A6] <div style="text-align:left; display:inline-block; margin-bottom:6px;"><code>virtual void f(int) const noexcept;   // base<br>int f(int) const noexcept;            // candidato (f)</code></div><br>Data <code>virtual void f(int) const noexcept;</code> nella base, <code>int f(int) const noexcept</code> nella derivata (return type diverso) è un override legale?	No: il return type deve essere identico o <b>covariante</b>, e la covarianza vale solo per puntatori/riferimenti a classi in relazione di derivazione, non per <code>int</code> vs <code>void</code>.

[C++][A6] <div style="text-align:left; display:inline-block; margin-bottom:6px;"><code>void f(int) const noexcept &amp;;         // lvalue ref-qualified<br>void f(int) const noexcept &amp;&amp;;        // rvalue ref-qualified</code></div><br>I <b>ref-qualifier</b> (<code>&amp;</code> / <code>&amp;&amp;</code>) di una funzione membro fanno parte della firma ai fini dell'override?	Sì: devono coincidere esattamente tra base e derivata.

[C++][A7] <div style="text-align:left; display:inline-block; margin-bottom:6px;"><code>class B {<br>public:  void call() { f(); }<br>private: virtual void f() { std::cout &lt;&lt; "B"; }<br>};<br>class D : public B {<br>public: void f() override { std::cout &lt;&lt; "D"; }<br>};<br>B* p = new D;<br>p-&gt;call();                     // (1)<br>p-&gt;f();                        // (2)<br>static_cast&lt;D*&gt;(p)-&gt;f();       // (3)</code></div><br>Nel pattern <b>NVI</b> (Non-Virtual Interface), l'interfaccia pubblica è virtuale o no? E i punti di variazione?	L'interfaccia pubblica è <b>non virtuale</b> (es. <code>call()</code>); i punti di variazione sono funzioni virtuali <b>private</b>, ridefinite dalle derivate ma non richiamabili direttamente dall'esterno.

[C++][A7] <div style="text-align:left; display:inline-block; margin-bottom:6px;"><code>class B {<br>public:  void call() { f(); }<br>private: virtual void f() { std::cout &lt;&lt; "B"; }<br>};<br>class D : public B {<br>public: void f() override { std::cout &lt;&lt; "D"; }<br>};<br>B* p = new D;<br>p-&gt;call();                     // (1)<br>p-&gt;f();                        // (2)<br>static_cast&lt;D*&gt;(p)-&gt;f();       // (3)</code></div><br>Perché una funzione virtuale <code>private</code> è comunque perfettamente overridabile da una classe derivata?	Perché controllo di accesso e dispatch dinamico sono <b>ortogonali</b>: l'accesso è verificato sul tipo statico al punto di chiamata, il dispatch sul tipo dinamico dell'oggetto. La derivata deve solo <b>ridefinirla</b>, non chiamarla.

[C++][A7] <div style="text-align:left; display:inline-block; margin-bottom:6px;"><code>class B {<br>public:  void call() { f(); }<br>private: virtual void f() { std::cout &lt;&lt; "B"; }<br>};<br>class D : public B {<br>public: void f() override { std::cout &lt;&lt; "D"; }<br>};<br>B* p = new D;<br>p-&gt;call();                     // (1)<br>p-&gt;f();                        // (2)<br>static_cast&lt;D*&gt;(p)-&gt;f();       // (3)</code></div><br>Con <code>B* p = new D;</code> (<code>D</code> overrida la <code>private virtual f()</code> di <code>B</code>), perché <code>p->f()</code> è un errore di compilazione mentre <code>p->call()</code> (che internamente chiama <code>f()</code>) stampa "D"?	<code>p->f()</code> tenta un accesso diretto a <code>f()</code>, <code>private</code> nel tipo <b>statico</b> di <code>p</code> (<code>B</code>): errore. <code>p->call()</code> chiama <code>f()</code> da dentro <code>B</code>, dove è accessibile; il dispatch interno risolve comunque a <code>D::f</code>.

[C++][A8] Perché un costruttore non può essere <code>virtual</code> in C++?	Perché il dispatch virtuale richiede un oggetto già costruito con un vptr valido, ed è esattamente il costruttore a installarlo: un costruttore virtuale sarebbe circolare.

[C++][A8] Come si implementa un "costruttore virtuale" (clone polimorfico) in C++?	Con l'idioma <code>clone()</code>: metodo virtuale che restituisce <code>new ClassName(*this)</code>; ogni derivata lo ridefinisce con <b>return type covariante</b> (es. <code>Der*</code> invece di <code>Base*</code>).

[C++][A8] Perché una member function <b>template</b> non può essere dichiarata <code>virtual</code>?	Perché genera istanziazioni potenzialmente illimitate, scoperte anche in unità di traduzione diverse e dopo la definizione della classe: la vtable dovrebbe avere dimensione/layout non determinabili quando la classe viene definita.

[C++][A8] Una funzione virtuale può essere <code>inline</code>? Con quale effetto reale?	Sì: <code>inline</code> resta utile per le chiamate risolte staticamente o dopo devirtualizzazione; il compilatore deve comunque emettere anche una copia out-of-line, perché l'indirizzo finisce nella vtable.

[C++][A8] Differenza pratica tra <code>override</code> e <code>final</code> per il compilatore?	<code>override</code> è solo un controllo. <code>final</code> è un'informazione semantica (nessuno potrà più fare l'override) che permette al compilatore di <b>devirtualizzare</b> (e inlineare) la chiamata, anche senza LTO.

[C++][A8] Perché <code>delete[] pBase</code> su un array di <code>Derived</code> è UB anche con distruttore virtuale?	Il problema è l'<b>indicizzazione</b>, non la distruzione: l'aritmetica dei puntatori nell'array usa <code>sizeof</code> del tipo <b>statico</b> (<code>Base</code>), quindi <code>pBase[1]</code> calcola l'offset sbagliato se <code>sizeof(Derived) &gt; sizeof(Base)</code>.

[C++][A9] <div style="text-align:left; display:inline-block; margin-bottom:6px;"><code>struct A { A(const char* who) { std::cout &lt;&lt; who &lt;&lt; " "; } };<br>struct B : virtual A { B() : A("da B") {} };<br>struct C : virtual A { C() : A("da C") {} };<br>struct D : B, C  { D() : A("da D"), B(), C() {} };<br>struct E : D     { E() : A("da E"), D()      {} };<br>int main() { E e; }</code></div><br>Nell'ereditarietà virtuale (<code>D : B, C</code> entrambe virtual <code>A</code>; <code>E : D</code>), chi inizializza il sotto-oggetto virtuale <code>A</code> quando si crea un <code>E</code>?	Il costruttore della classe <b>most derived</b> (<code>E</code>). I mem-initializer per <code>A</code> scritti in <code>B</code>, <code>C</code>, <code>D</code> vengono <b>ignorati</b> in questa costruzione.

[C++][A9] <div style="text-align:left; display:inline-block; margin-bottom:6px;"><code>struct A { A(const char* who) { std::cout &lt;&lt; who &lt;&lt; " "; } };<br>struct B : virtual A { B() : A("da B") {} };<br>struct C : virtual A { C() : A("da C") {} };<br>struct D : B, C  { D() : A("da D"), B(), C() {} };<br>struct E : D     { E() : A("da E"), D()      {} };<br>int main() { E e; }</code></div><br>Cosa succede se una classe most-derived non nomina esplicitamente la base virtuale, e quella base non ha un costruttore di default?	Il programma è <b>ill-formed</b>. Ogni classe concreta della gerarchia, a qualunque profondità, è obbligata a nominare esplicitamente la base virtuale se questa non ha un ctor di default.

[C++][A9] <div style="text-align:left; display:inline-block; margin-bottom:6px;"><code>struct A { A(const char* who) { std::cout &lt;&lt; who &lt;&lt; " "; } };<br>struct B : virtual A { B() : A("da B") {} };<br>struct C : virtual A { C() : A("da C") {} };<br>struct D : B, C  { D() : A("da D"), B(), C() {} };<br>struct E : D     { E() : A("da E"), D()      {} };<br>int main() { E e; }</code></div><br>Ordine di costruzione dei sotto-oggetti in una gerarchia con basi virtuali?	Prima le basi <b>virtuali</b> (depth-first sinistra→destra sulla gerarchia della most derived), poi le basi non virtuali in ordine di dichiarazione, poi i membri, infine il corpo del costruttore. La distruzione è in ordine esattamente inverso.

[C++][A10] <div style="text-align:left; display:inline-block; margin-bottom:6px;"><code>// layout schematico di Bat con ereditarietà virtuale:<br>// (vpointer, Mammal, vpointer, WingedAnimal, Bat, Animal)<br><br>Animal* pa = &amp;bat;<br>Bat* p1 = static_cast&lt;Bat*&gt;(pa);<br>Bat* p2 = dynamic_cast&lt;Bat*&gt;(pa);</code></div><br>Nell'esempio <code>Animal</code>/<code>Mammal</code>/<code>WingedAnimal</code>/<code>Bat</code> con ereditarietà virtuale, perché <code>Animal</code> finisce <b>in fondo</b> al layout di <code>Bat</code> invece che all'inizio?	Perché <code>Mammal</code> e <code>WingedAnimal</code> devono conservare il layout che avrebbero da soli; l'unica copia condivisa di <code>Animal</code> va in una posizione che non appartiene a nessuno dei due rami, cioè in fondo.

[C++][A10] <div style="text-align:left; display:inline-block; margin-bottom:6px;"><code>// layout schematico di Bat con ereditarietà virtuale:<br>// (vpointer, Mammal, vpointer, WingedAnimal, Bat, Animal)<br><br>Animal* pa = &amp;bat;<br>Bat* p1 = static_cast&lt;Bat*&gt;(pa);<br>Bat* p2 = dynamic_cast&lt;Bat*&gt;(pa);</code></div><br>Perché con ereditarietà virtuale servono <b>due vpointer</b> nel layout di <code>Bat</code>?	Perché ciascun ramo deve sapere "quanto dista da qui il mio <code>Animal</code>" (<b>vbase offset</b>), e questa distanza è diversa a seconda di come il sotto-oggetto è immerso nell'oggetto completo.

[C++][A10] <div style="text-align:left; display:inline-block; margin-bottom:6px;"><code>// layout schematico di Bat con ereditarietà virtuale:<br>// (vpointer, Mammal, vpointer, WingedAnimal, Bat, Animal)<br><br>Animal* pa = &amp;bat;<br>Bat* p1 = static_cast&lt;Bat*&gt;(pa);<br>Bat* p2 = dynamic_cast&lt;Bat*&gt;(pa);</code></div><br>Perché l'offset tra un sotto-oggetto e la sua base virtuale <b>non</b> è noto a compile time, mentre lo è nell'ereditarietà non virtuale?	Perché quando il compilatore traduce un metodo di <code>Mammal</code> non sa se sarà un oggetto autonomo o il sotto-oggetto di un <code>Bat</code> (dove <code>Animal</code> sta molto più in là): l'offset dipende dal contesto d'uso, noto solo a runtime.

[C++][A10] <div style="text-align:left; display:inline-block; margin-bottom:6px;"><code>// layout schematico di Bat con ereditarietà virtuale:<br>// (vpointer, Mammal, vpointer, WingedAnimal, Bat, Animal)<br><br>Animal* pa = &amp;bat;<br>Bat* p1 = static_cast&lt;Bat*&gt;(pa);<br>Bat* p2 = dynamic_cast&lt;Bat*&gt;(pa);</code></div><br>Perché <code>static_cast</code> da un puntatore a base virtuale verso la derivata è vietato (ill-formed)? Quale cast va usato?	Il compilatore dovrebbe sottrarre un offset che non conosce staticamente. [C++][A12] Qual è il criterio per decidere se ereditare virtualmente una base oppure no?	Se l'ereditarietà esprime una <b>restrizione di un insieme</b> (un <code>Bat</code> è un <code>Animal</code>, uno solo) la base va condivisa → <code>virtual</code>. [C++][A12] In una frase, differenza di rappresentazione in memoria tra base virtuale e non virtuale?	Non virtuale = <b>incorporata</b> (una copia per ramo, offset costante); virtuale = <b>condivisa</b> (una copia sola, offset letto a runtime).

L'attributo di <b>istanza</b>: le funzioni sono descrittori <b>non-data</b> (solo <code>__get__</code>), e per questi il <code>__dict__</code> dell'istanza ha la precedenza.

[Python][C4] <div style="text-align:left; display:inline-block; margin-bottom:6px;"><code>class A:<br>&nbsp;&nbsp;&nbsp;&nbsp;def f(self): print("A.f")<br>class B(A):<br>&nbsp;&nbsp;&nbsp;&nbsp;def f(self): print("B.f")<br><br>b = B()<br>b.f()                                  # (1)<br>A.f(b)                                 # (2)<br>B.f = A.f;  b.f()                      # (3)<br>b.f = lambda: print("inst");  b.f()    # (4)<br>del b.f<br>b.__class__ = A;  b.f()                # (5)</code></div><br>Se <code>f</code> fosse una <code>property</code> invece di un metodo semplice, un attributo di istanza omonimo vincerebbe comunque?	No: una <code>property</code> è un descrittore <b>data</b> (<code>__get__</code> <i>e</i> <code>__set__</code>), e i descrittori data vincono <b>sempre</b> sul dizionario dell'istanza.

[Python][C4] <div style="text-align:left; display:inline-block; margin-bottom:6px;"><code>class A:<br>&nbsp;&nbsp;&nbsp;&nbsp;def f(self): print("A.f")<br>class B(A):<br>&nbsp;&nbsp;&nbsp;&nbsp;def f(self): print("B.f")<br><br>b = B()<br>b.f()                                  # (1)<br>A.f(b)                                 # (2)<br>B.f = A.f;  b.f()                      # (3)<br>b.f = lambda: print("inst");  b.f()    # (4)<br>del b.f<br>b.__class__ = A;  b.f()                # (5)</code></div><br>Riassegnare <code>b.__class__ = A</code> a runtime cambia il dispatch dei metodi di <code>b</code>?	Sì: cambia il tipo dinamico dell'oggetto, e quindi il risultato del dispatch da quel momento in poi.

[Python][C5] <div style="text-align:left; display:inline-block; margin-bottom:6px;"><code>class A:<br>&nbsp;&nbsp;&nbsp;&nbsp;def __add__(self, other): return "A.__add__"<br>class B(A):<br>&nbsp;&nbsp;&nbsp;&nbsp;def __radd__(self, other): return "B.__radd__"<br>print(A() + B())</code></div><br>Per <code>A() + B()</code> con <code>B(A)</code> che ridefinisce solo <code>__radd__</code> (non <code>A</code>, che ha solo <code>__add__</code>), quale metodo viene chiamato?	<code>B.__radd__</code>. Regola: normalmente prima <code>__add__</code> della sinistra poi <code>__radd__</code> della destra, ma se destra è <b>sottoclasse propria</b> di sinistra con un <code>__radd__</code> diverso, il riflesso viene provato <b>per primo</b>.

[Python][C5] <div style="text-align:left; display:inline-block; margin-bottom:6px;"><code>class A:<br>&nbsp;&nbsp;&nbsp;&nbsp;def __add__(self, other): return "A.__add__"<br>class B(A):<br>&nbsp;&nbsp;&nbsp;&nbsp;def __radd__(self, other): return "B.__radd__"<br>print(A() + B())</code></div><br>Perché Python dà precedenza al metodo riflesso di una sottoclasse rispetto all'operatore della classe base?	Per garantire che una sottoclasse possa sempre avere l'ultima parola sulle operazioni che la coinvolgono, altrimenti non potrebbe raffinare il comportamento ereditato.

[Python][C6] <div style="text-align:left; display:inline-block; margin-bottom:6px;"><code>class A:<br>&nbsp;&nbsp;&nbsp;&nbsp;@classmethod<br>&nbsp;&nbsp;&nbsp;&nbsp;def create(cls, *args): return cls(*args)<br>&nbsp;&nbsp;&nbsp;&nbsp;def __repr__(self): return type(self).__name__<br>class B(A): pass<br>print(B.create())</code></div><br>In <code>@classmethod def create(cls, *args): return cls(*args)</code>, chiamato come <code>B.create()</code> (<code>B</code> sottoclasse di <code>A</code>), cosa viene istanziato?	Un'istanza di <code>B</code>: <code>cls</code> è legato al tipo su cui è avvenuta effettivamente la chiamata. È il "costruttore virtuale" polimorfico che C++ non ha nativamente.

[Python][C6] <div style="text-align:left; display:inline-block; margin-bottom:6px;"><code>class A:<br>&nbsp;&nbsp;&nbsp;&nbsp;@classmethod<br>&nbsp;&nbsp;&nbsp;&nbsp;def create(cls, *args): return cls(*args)<br>&nbsp;&nbsp;&nbsp;&nbsp;def __repr__(self): return type(self).__name__<br>class B(A): pass<br>print(B.create())</code></div><br>Perché una factory <code>@staticmethod</code> che fa <code>return A()</code> è peggiore, ai fini del polimorfismo, di una <code>@classmethod</code> che fa <code>return cls()</code>?	<code>@staticmethod</code> non riceve informazione sul tipo chiamante: restituirebbe sempre <code>A</code>, e ogni sottoclasse dovrebbe riscrivere la factory da zero.

[Python][C7] <div style="text-align:left; display:inline-block; margin-bottom:6px;"><code>from abc import abstractmethod<br>class Base:<br>&nbsp;&nbsp;&nbsp;&nbsp;@abstractmethod<br>&nbsp;&nbsp;&nbsp;&nbsp;def f(self): ...<br>class Impl(Base): pass<br>Impl()</code></div><br>Perché <code>class Impl(Base): pass</code> (con <code>Base</code> che ha un <code>@abstractmethod</code>) non impedisce <code>Impl()</code>?	Il controllo è fatto da <code>ABCMeta</code> alla creazione della classe (popola <code>__abstractmethods__</code>); <code>@abstractmethod</code> da solo imposta solo <code>__isabstractmethod__ = True</code>: senza <code>ABCMeta</code> nessuno legge quel flag.

[Python][C7] <div style="text-align:left; display:inline-block; margin-bottom:6px;"><code>from abc import abstractmethod<br>class Base:<br>&nbsp;&nbsp;&nbsp;&nbsp;@abstractmethod<br>&nbsp;&nbsp;&nbsp;&nbsp;def f(self): ...<br>class Impl(Base): pass<br>Impl()</code></div><br>Come si corregge una classe base con <code>@abstractmethod</code> perché <code>Impl()</code> sollevi davvero errore?	Facendo ereditare <code>Base</code> da <code>abc.ABC</code>, o impostando <code>metaclass=abc.ABCMeta</code>.

[Python][C7] <div style="text-align:left; display:inline-block; margin-bottom:6px;"><code>from abc import abstractmethod<br>class Base:<br>&nbsp;&nbsp;&nbsp;&nbsp;@abstractmethod<br>&nbsp;&nbsp;&nbsp;&nbsp;def f(self): ...<br>class Impl(Base): pass<br>Impl()</code></div><br>Ai fini dell'overriding, che differenza c'è tra <code>__init_subclass__</code> e una metaclasse?	<code>__init_subclass__</code> è un hook per-sottoclasse (invocato alla creazione di ogni classe figlia). Una metaclasse controlla la creazione dell'oggetto-classe stesso: più potente, ma può causare conflitti nell'ereditarietà multipla.

[C][D1] In un dispatch scritto a mano con <code>struct Shape { const ShapeVT *vptr; }</code> e <code>Circle</code> che la incorpora, perché il sotto-oggetto base deve essere il <b>primo</b> membro?	Perché lo standard C garantisce assenza di padding all'inizio di una struct: <code>(Shape*)circle == &amp;circle->base</code>, la conversione derivata↔base è un no-op, senza aggiustamento del puntatore (nessun thunk).

[C][D1] In C, chi inizializza il vptr di un oggetto "derivato", e cosa succede se ci si dimentica?	Lo inizializza <b>a mano il programmatore</b> (nella funzione "costruttore"). Se dimenticato, il vptr resta indeterminato e la prima chiamata virtuale salta nel vuoto. In C++ è il compilatore a farlo in ogni costruttore.

[C][D1] Come si emula un distruttore virtuale e un <code>dynamic_cast</code> in C puro con una vtable scritta a mano?	Distruttore virtuale = una entry <code>dtor</code> invocata come <code>s->vptr->dtor(s)</code>. <code>dynamic_cast</code> = confronto del vptr (o di un tag <code>type_name</code>) con quello atteso; per gerarchie multi-livello, un puntatore "parent" da risalire.

[C][D2] <div style="text-align:left; display:inline-block; margin-bottom:6px;"><code>void draw_all(Shape **v, size_t n);<br>Circle *arr[3] = { c1, c2, c3 };<br>draw_all((Shape **)arr, 3);</code></div><br>Perché <code>draw_all((Shape**)arr, 3)</code> (con <code>arr</code> array di <code>Circle*</code>) è formalmente scorretto in C, anche se "funziona" ovunque?	<code>Circle*</code> e <code>Shape*</code> sono tipi di puntatore <b>non compatibili</b>: <code>v[i]</code> legge un oggetto di effective type <code>Circle*</code> attraverso un lvalue <code>Shape*</code>, violando lo <b>strict aliasing</b> (C11 6.5p7) → UB.

[C][D2] <div style="text-align:left; display:inline-block; margin-bottom:6px;"><code>void draw_all(Shape **v, size_t n);<br>Circle *arr[3] = { c1, c2, c3 };<br>draw_all((Shape **)arr, 3);</code></div><br>La garanzia "l'indirizzo del primo membro coincide con l'indirizzo della struct" basta a rendere sicuro il cast di un array <code>Circle**</code> in <code>Shape**</code>?	No: riguarda l'indirizzo di <b>un oggetto</b>, non la compatibilità tra <b>tipi di puntatore</b>. Un array di <code>Circle*</code> non è un array di <code>Shape*</code>: la conversione va fatta elemento per elemento.

[C][D3] Traducendo letteralmente <code>virtual double area() const;</code> del C++ in C: cosa diventa <code>this</code>? Cosa diventa <code>const</code>?	<code>this</code> diventa il primo parametro esplicito (<code>Shape *self</code>); <code>const</code> diventa <code>const Shape *self</code>, nessuna differenza a runtime, solo type checking.

[C][D3] Nella traduzione letterale della vtable dal C++ al C, quanti puntatori pesa il polimorfismo virtuale per oggetto e per classe?	Un puntatore per <b>oggetto</b> (il vptr); una tabella di N puntatori per <b>classe</b> (condivisa da tutte le istanze). Nessun altro overhead — "zero-overhead principle".

[C][D3] Perché mantenere lo <b>stesso indice</b> per lo stesso metodo lungo tutta la gerarchia è cruciale nell'"ereditarietà" di una vtable scritta a mano?	È questa invarianza dell'indice a rendere il dispatch <b>O(1)</b>, indipendente dalla profondità della gerarchia: la derivata copia la vtable della base e sovrascrive solo gli slot ridefiniti, senza spostarli.

[C][D4] <code>struct file_operations</code> del kernel Linux e il comparatore di <code>qsort</code>: quale corrisponde all'overriding e quale alla strategy/callback?	<code>file_operations</code> è <b>overriding</b>: una vtable condivisa da tutte le istanze di un "tipo" di file, raggiunta via <code>f_op</code>. Il comparatore di <code>qsort</code> è <b>strategy/callback</b>: passato per parametro alla singola chiamata, non associato al tipo.

[C][D4] Cosa fa <code>container_of(ptr, type, member)</code>, e a quale operazione C++ corrisponde?	Risale dall'indirizzo di un membro all'indirizzo della struct che lo contiene (sottraendo <code>offsetof</code>). Corrisponde al <b>downcast</b> base→derivata quando il sotto-oggetto base non è il primo membro.

[C][D5] Perché in C non si ottiene overriding automatico nemmeno con <code>static inline</code> negli header?	Perché ogni chiamata C è <b>early binding</b>: il nome è risolto dal linker a un singolo simbolo; non esiste alcun canale che leghi un oggetto a un insieme di funzioni.

[C][D5] Quali due impedimenti strutturali del C (oltre all'early binding) impediscono un overriding automatico "alla C++"?	(1) assenza di <b>name mangling</b> (niente overload, quindi niente override); (2) assenza di <b>costruttori</b> (nessun punto garantito in cui installare il vptr).

[Trasv][E1] Meccanismo di dispatch a runtime nei quattro linguaggi?	C++: vtable per classe + vptr per oggetto, indice noto a compile time. Java: <code>invokevirtual</code>/<code>invokeinterface</code>, JIT con inline cache e CHA. Python: lookup nel <code>__dict__</code> lungo l'MRO, poi protocollo dei descrittori. C: struct di puntatori a funzione scritta a mano.

[Trasv][E1] Costo per chiamata del dispatch dinamico nei quattro linguaggi?	C++: 2 load + chiamata indiretta, devirtualizzabile con <code>final</code>/LTO. Java: come C++ ma spesso inlinato per speculazione (CHA). Python: il più alto (hash lookup + bound method). C: identico al C++, scritto a mano.

[Trasv][E1] In quali linguaggi si può aggiungere/rimpiazzare un metodo <b>a runtime</b>?	Python: sempre (classi mutabili, monkey patching). Java: no per una classe già caricata. C++: no, layout fissato a compile time. C: sì, se la vtable non è <code>const</code>.

[Trasv][E1] In quali linguaggi esiste il <b>method/field hiding</b> distinto dall'overriding?	C++: sì (name hiding, campi, membri non virtuali). Java: sì (campi, <code>static</code>, <code>private</code>). Python: non esiste, solo shadowing istanza/classe/MRO. C: non applicabile.

[Trasv][E1] Come si chiama esplicitamente l'implementazione della classe base nei quattro linguaggi?	C++: <code>Base::f()</code>. Java: <code>super.f()</code> (<code>B.super.f()</code> per i default). Python: <code>super().f()</code> — segue l'MRO, non "la superclasse"! — o <code>A.f(self)</code>. C: <code>parent_vt->f(self)</code> esplicito.

[Trasv][E2] Perché in C++ le funzioni sono non virtuali per <b>default</b> (zero-overhead principle)?	Chi non usa il polimorfismo non paga né il vptr né la chiamata indiretta; <code>virtual</code> è opt-in. Prezzo: renderlo virtuale dopo è un cambio di ABI, e dimenticare <code>virtual ~Base()</code> è UB.

[Trasv][E2] Perché in Java le funzioni sono virtuali per default, e come la JVM recupera il costo del dispatch?	Per uniformità; il costo è recuperabile a runtime con <b>Class Hierarchy Analysis</b> (devirtualizza se una sola classe caricata implementa il metodo) e <b>inline cache</b> mono/bimorfiche.

[Trasv][E2] Cos'è il "<b>fragile base class problem</b>", e come si manifesta diversamente coi due default?	Una modifica interna alla base rompe le sottoclassi. Col default virtuale, ogni metodo pubblico è un punto di estensione non intenzionale (es. <code>HashSet.addAll</code> che chiama <code>add</code>). Col default non virtuale, il rischio si sposta sull'hiding silenzioso.

[Trasv][E3] Data <code>Base.process(Base b)</code> e <code>Derived.process(Derived d)</code>, in quale dei quattro linguaggi è davvero un override che sostituisce quello della base?	In nessuno correttamente: in C++/Java è un <b>overload</b> (si aggiunge). In Python il nome sostituisce davvero quello della base ma <b>viola LSP</b> (segnalato dai type checker). In C il concetto non esiste.

[Trasv][E3] Il principio di sostituzione di Liskov richiede parametri covarianti o controvarianti? E il return type?	Parametri <b>controvarianti</b> (la derivata accetta almeno tutto ciò che accetta la base); return type <b>covariante</b>.

[Trasv][E3] Perché restringere il parametro a <code>Derived</code> (invece di <code>Base</code>) non è type-safe?	Con <code>Base b = new Derived(); b.process(new Base());</code> il metodo riceverebbe un oggetto <code>Base</code> che non sa trattare — stesso buco degli array covarianti Java (<code>ArrayStoreException</code>).

[Trasv][E4] Definisci <b>dominanza</b> in C++: esiste un analogo in un altro linguaggio del corso?	Con ereditarietà virtuale, un membro di una classe più derivata "domina" quello della base virtuale, risolvendo un'ambiguità altrimenti presente. Esiste solo in C++; un analogo (banale, ereditarietà singola) esiste in Java.

[Trasv][E4] Definisci <b>bridge method</b>: in quale linguaggio esiste e perché viene generato?	Metodo sintetico generato dal compilatore <b>Java</b> per riconciliare l'erasure dei generici (o i return covarianti) con la firma richiesta dalla JVM per il dispatch.

[Trasv][E4] Definisci <b>thunk</b> nel contesto dell'ereditarietà multipla in C++.	Trampolino che aggiusta il puntatore <code>this</code> (sottraendo un offset) nell'ereditarietà multipla/virtuale, prima di saltare all'override reale.

[Trasv][E4] Definisci <b>final overrider</b> in C++: cosa succede se non è unico?	Per ogni funzione virtuale e ogni classe, l'unica implementazione effettivamente installata in vtable. Se non è unico, il programma è <b>ill-formed</b>.

[Trasv][E4] Differenza tra "hiding/shadowing" e "overriding"? Un esempio in C++ e uno in Java.	Hiding: un nome in scope più interno oscura quello esterno <b>senza</b> polimorfismo (risoluzione statica). Overriding: risoluzione sul tipo dinamico. C++: name hiding degli overload. Java: campi e metodi <code>static</code>.

[Trasv][E4] In quale dei quattro linguaggi esiste l'<b>overloading</b>? Come si emula dove manca?	Esiste in C++ e Java. In Python <b>non esiste</b> (l'ultima definizione vince): si emula con <code>functools.singledispatch</code>. In C non esiste affatto.
